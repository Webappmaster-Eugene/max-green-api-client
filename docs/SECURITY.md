# Безопасность

## Доступ

- Публичная регистрация отсутствует. Пользователей создаёт администратор.
- Все маршруты MAX и управления пользователями требуют проверенной JWT-cookie.
- Cookie в HTTPS: `__Host-max-auth`, Secure, HttpOnly, SameSite=Strict, Path=/,
  без Domain; срок восемь часов. JWT не возвращается в JSON и не попадает
  в localStorage/sessionStorage.
- JOSE проверяет HS256, issuer, audience, subject, jti и срок. Для jti требуется
  действующая серверная сессия; пользователь должен оставаться активным с той же
  версией доступа. Logout отзывает токен. Смена пароля и запрет доступа отзывают
  все токены пользователя.
- Сервер не запускается без JWT-secret и доступного валидного хранилища.
  При повреждении JSON новый набор пользователей не создаётся автоматически.
- Пароли имеют индивидуальную соль и scrypt-хеш. В API выдаётся только безопасный
  профиль. Минимум нового пароля — 12 символов.

## Запросы

Изменения требуют CSRF-токен в заголовке. Токен привязан к JWT-сессии и сравнивается
без зависимости времени от совпадающих символов. Login также требует собственного
непростого заголовка и правильного Origin; CORS не включён. Cross-site запросы
отклоняются. Внешний HTTPS reverse proxy должен сохранять корректный Origin.

Перебор ограничен по IP и логину. Неизвестный/отключённый пользователь и неверный
пароль дают одинаковый ответ. Другие API, подключение и отправка также ограничены
по частоте. IP берётся из последнего адреса X-Forwarded-For, добавленного доверенным
прокси. Не публикуйте порт контейнера напрямую для обхода этого прокси.

Zod проверяет тела, поля multipart, query, DTO и ответы GREEN-API. JSON до 32 КиБ;
upload до 10 МБ плюс небольшой запас для multipart. Входные схемы не принимают
подмену владельца в теле запроса.

## Изоляция

Владелец берётся из проверенной сессии сайта. Произвольный connectionId, chatId
или messageId не даёт доступ к данным другого пользователя. Цитирование,
редактирование, удаление, пересылка, реакции и вложения проверяются по известным
сообщениям и чатам текущего подключения. Администратор управляет доступом к сайту,
но не получает API для просмотра чужой переписки.

Токен GREEN-API хранится только в памяти. Token-bearing URL и провайдерские
тела ошибок не логируются и не возвращаются пользователю. Отзыв доступа отменяет
незавершённые HTTP-запросы; уже принятая провайдером отправка может завершиться.

## Файлы и браузер

Адрес API ограничен HTTPS-хостами GREEN-API, адрес загрузки — HTTPS api/media-хостами GREEN-API.
Redirect запрещён. Ссылки вложений принимаются только с media-хостов GREEN-API
и его известных sw-media bucket в Yandex Cloud. Пользователь не передаёт URL
скачивания: маршрут берёт его из проверенной истории собственного подключения.

Скачивание ограничено 10 МБ, включая поток без Content-Length. Выдача — attachment
с application/octet-stream, nosniff и CSP sandbox. Превью разрешено только для
растровых типов изображений. Прикрепляемые расширения ограничены; SVG, HTML,
исполняемые файлы и скрипты не принимаются. Антивирусного сканирования нет.

React выводит текст без исполнения HTML. CSP ограничивает скрипты, подключения,
медиа и шрифты своим origin; object-src и frame-src запрещены. Стилям разрешён
inline для Mantine. Frame-ancestors/X-Frame-Options запрещают встраивание сайта.
Есть HSTS, Referrer-Policy и Permissions-Policy; ответы API не кэшируются.

## Эксплуатация

Контейнер работает от пользователя node. Секреты передаются через окружение
Dokploy. `.env*`, приватные реквизиты и `data/` исключены из Git и Docker context.
Persistent volume для данных должен быть доступен только приложению и администратору.
Резервные копии users.json содержат хеши и требуют такой же защиты.

Однопроцессное хранилище и RAM-сессии подходят для небольшого закрытого сервиса.
Это не SSO-платформа: MFA, восстановление пароля по email, журнал аудита,
антивирус и распределённые лимиты не входят в реализацию.
