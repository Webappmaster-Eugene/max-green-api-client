# Запуск и развёртывание

## Локальная установка

Нужен Node.js 22.12 или новее, npm и Git. Telegram, PostgreSQL и Redis не нужны.

```sh
git clone https://github.com/Webappmaster-Eugene/max-green-api-client.git
cd max-green-api-client
npm ci
npm run auth:setup
npm run build
npm run start:local
```

Откройте http://127.0.0.1:18792. Команда `auth:setup` создаёт `.env.local`
и `.admin-credentials` с правами 0600. Первый содержит случайный JWT-secret
и scrypt-хеш начального пароля, второй — логин и пароль для владельца.
Команда не перезаписывает уже существующие файлы. Реквизиты не печатаются в терминал
и исключены из Git/Docker context. После первого входа измените пароль через UI.

В режиме разработки запустите два терминала:

```sh
npm run dev
```

```sh
npm run dev:ui
```

Фронт: http://127.0.0.1:5174. Launcher разработки задаёт этот PUBLIC_ORIGIN;
Vite проксирует API на 18792. Используйте именно 127.0.0.1, чтобы Origin
совпадал. Production `npm start` получает настройки из окружения хостинга.

## Переменные

| Имя                 | Назначение                                                          |
| ------------------- | ------------------------------------------------------------------- |
| PUBLIC_ORIGIN       | Полный origin сайта без завершающего `/` и пути, HTTPS в production |
| AUTH_JWT_SECRET     | Случайный ключ не менее 32 байт; не пароль пользователя             |
| ADMIN_LOGIN         | Первый администратор; используется только при отсутствии users.json |
| ADMIN_PASSWORD_HASH | Начальный scrypt-хеш, создаётся командой auth:setup                 |
| DATA_DIR            | Каталог для users.json, в контейнере `/app/data`                    |
| HOST                | В контейнере `0.0.0.0`                                              |
| PORT                | В контейнере `3000`                                                 |
| NODE_ENV            | `production` для выката                                             |

Пароль GREEN-API и его ключ не являются переменными окружения приложения:
пользователь вводит реквизиты своего MAX в защищённой форме.

## Dokploy

1. Application из этого Git-репозитория, ветка `main`, сборка `Dockerfile`,
   контекст `.`. Порт контейнера 3000.
2. Домен `max.nadtocheev.ru`, HTTPS и Let's Encrypt. PUBLIC_ORIGIN должен
   совпадать с адресом в браузере.
3. Перед первым запуском передайте JWT-secret, ADMIN_LOGIN и ADMIN_PASSWORD_HASH
   в закрытое окружение Dokploy. Используйте значения из локальной подготовки;
   не помещайте их в Dockerfile или Git.
4. Добавьте persistent **volume** к `/app/data`. Каталог должен быть доступен
   пользователю контейнера node (UID 1000). Без volume пользователи потеряются
   при пересоздании контейнера.
5. Оставьте **одну реплику**. Это однопроцессное файловое хранилище, а очередь
   GREEN-API имеет одного потребителя.
6. Deploy. Проверьте `/health`, страницу входа и ответ 401 от `/api/max`
   без cookie (с заголовком `X-Max-Client: 1`). Вход, управление пользователями
   и cookie проверяются отдельно от состояния health.

Сервис запускается без root. JWT-secret и хранилище обязательны: некорректная
конфигурация останавливает запуск. Существующий users.json при перезапуске
не заменяется bootstrap-настройками.

## Резервные копии и обновление

Сохраняйте защищённую копию `DATA_DIR/users.json` и JWT-secret. users.json
содержит логины, роли и хеши, но не MAX-ключи и не историю сообщений.
Копия должна иметь ограниченный доступ. Подключения MAX и JWT-сессии в RAM
после рестарта не восстанавливаются: пользователи входят и подключают MAX снова.

Перед обновлением прогоните проверки ниже, отправьте проверенный commit
и разверните его в Dokploy. Пользователи сохраняются через volume. После выката
проверьте actual commit, health, анонимный отказ, вход и выход.

## Проверки

```sh
npm run format:check
npm run smoke
npm test
npm run test:ui
npm run build
npx playwright install chromium
npm run test:e2e
docker build -t max-client .
```

Backend-тесты проверяют JWT, срок, выход, смену пароля, отзыв доступа, CSRF,
ownership, scrypt, приватность файла пользователей, SSRF, лимиты вложений,
идемпотентность отправки и контракты действий. FSD-тест проверяет архитектурные
границы и размещение типов; отдельная проверка запрещает комментарии и explicit any
в production source.

React-тесты проверяют безопасный вход, контракт ответа, CSRF и сохранение файла
после неопределённого результата отправки. Playwright использует отдельный
временный сервер/хранилище, настоящую авторизацию и подменённый MAX API. Сценарии
проходят на компьютере и телефоне и не отправляют сообщения в реальный MAX.

CI выполняет проверки из `.github/workflows/ci.yml`. Аудит npm проверяет runtime
и dev-зависимости. Версия esbuild закреплена на исправленном выпуске, совместимость
проверяется сборкой и тестами.
