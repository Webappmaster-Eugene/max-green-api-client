# Архитектура

## Фронт: Feature-Sliced Design

Вход — `webapp/src/main.tsx`. Он подключает только слой `app`.

| Слой     | Содержимое                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| app      | Провайдер Mantine, тема, CSS, выбор экрана по состоянию входа                                                                        |
| pages    | Экран входа и страница переписки                                                                                                     |
| widgets  | Рабочее место чатов и панель аккаунта                                                                                                |
| features | Вход, подключение MAX, управление перепиской, составление сообщений, действия с сообщениями, смена пароля, управление пользователями |
| entities | API учётной записи, API переписки, представление чата и сообщения                                                                    |
| shared   | Валидируемый HTTP-клиент, общие контракты, форматирование и переключатель темы                                                       |

Срезы экспортируют публичный API через `index.ts`. Импорты идут вниз по слоям;
разные срезы одного слоя не импортируют друг друга. Внутренние компоненты одного
виджета могут импортироваться напрямую внутри своего среза. Проверка направления
импортов включена в тесты.

UI построен на Mantine, иконки — Tabler, шрифт Manrope поставляется локально.
React 19, TypeScript strict, ESM. Тёмная и светлая темы доступны пользователю.
CSS содержит только раскладку и оформление переписки поверх Mantine.

## Контракты и типы

`contracts/` — Zod-схемы входа, пользователей, JWT claims, окружения, запросов
MAX, DTO, ответов и данных провайдера. `types/` содержит типы, выведенные через
`z.infer`, и внутренние серверные модели. Типы UI-пропсов находятся в отдельных
`model/types.ts` своих срезов. Источник структуры DTO — схема, а не дублирующий
интерфейс.

Фронт получает контракты через `shared/contracts`. HTTP-клиент проверяет envelope
и DTO перед передачей данных компонентам. Сервер проверяет входные JSON, поля
multipart и query. Ответы GREEN-API проверяются отдельными схемами до преобразования
в DTO. Детали ошибок провайдера и token-bearing URL не попадают в ответы браузеру.

## Сервер

Hono обслуживает API и статическую сборку Vite. Слои сервера:

- `server/auth` — scrypt, атомарное хранилище пользователей, JWT и отзыв сессий;
- `server/lib` — безопасные ошибки и ограничение частоты запросов;
- `server/app.ts` — заголовки безопасности, проверка входа/CSRF/ролей и HTTP-роуты;
- `src/max/client.ts` — HTTPS-запросы к GREEN-API без редиректов;
- `src/max/session.ts` — подключение, ownership, очередь, история и действия;
- `src/max/message.ts` — преобразование истории и уведомлений;
- `src/max/media.ts` — ограничения файлов и безопасное скачивание.

## Жизненный цикл данных

Пользователи и scrypt-хеши сохраняются в `DATA_DIR/users.json`. Запись выполняется
в отдельный файл с правами 0600, затем атомарно заменяет основной файл. Изменения
сериализуются; публичный API никогда не отдаёт хеши. Это хранилище предназначено
для одного процесса/одной реплики. PostgreSQL и Redis этому приложению не нужны.

JWT подписывается HS256 с issuer и audience, находится только в HttpOnly-cookie.
Реестр JWT-сессий хранится в AES-256-GCM файле `auth-sessions.enc` с отдельным
ключом `auth-sessions.key`. Поэтому перезапуск сервера не завершает вход. Cookie
действует 365 дней и обновляется при запросе сессии, если прошло не менее суток.
Явный выход удаляет JTI из реестра; этот отзыв сохраняется после перезапуска. Статус и версия пользователя проверяются
на каждом запросе. Отзыв доступа и смена пароля инвалидируют старые токены.

Подключение MAX привязано к серверному ID пользователя. Реквизиты и ключ сохраняются
в `max-connections.enc`, ключ шифрования — `max-connections.key`, права 0600.
Срока истечения у подключения нет. Файлы должны жить в постоянном DATA_DIR.
`SavedConnections` хранит профиль и активный ключ; `EncryptedStore` валидирует
контракт Zod, шифрует AES-256-GCM с nonce и AAD, пишет атомарно с fsync. Хранилище
рассчитано на один процесс/реплику. Потеря ключа или повреждение файла запрещает
его использование и не создаёт пустую замену существующим данным.

`MaxSessions.restore` лениво восстанавливает только открываемое подключение и
объединяет параллельные запросы восстановления. Сохранённый активный инстанс
зарезервирован за владельцем даже до загрузки в память. После перезапуска создаётся
новый connectionId: старые запросы отправки отвергаются, чтобы не повторить отправку
при потерянном RAM-кэше requestId. Ошибки провайдера не удаляют сохранённый ключ.
Явный logout/отзыв доступа отменяет запросы и удаляет ключ, сохраняя профиль для
входа по одному ключу. Новый вход на другом устройстве того же пользователя
обращается к его подключению сайта. История, адреса вложений и попытки отправки
остаются в RAM; история восстанавливается из провайдера при выборе чата.

Очередь уведомлений читается последовательно. Сообщение сохраняется до ACK,
повторный receipt не создаёт дубль. История и уведомления используют исходные
ID. Статусы не откатываются назад. Отправка текста, файла и пересылка используют
requestId и сигнатуру содержимого; неопределённый результат не вызывает
автоматическую повторную отправку.

Mini App Советника использует свой сервер и независимую сессию. Этот репозиторий
развивается самостоятельно; копирование старого React-компонента из Советника
поверх FSD-структуры не является способом обновления.

## Ограничения

Одна реплика, до 100 пользователей, 500 JWT-сессий, 50 MAX-подключений,
10000 чатов/контактов и сообщений на подключение, 300 попыток отправки за сессию.
У провайдера история до 5000 событий/трёх месяцев. Polling работает только
в видимой вкладке. Постоянного архива сообщений, фоновых push и высокой доступности
не реализовано. При масштабировании потребуется внешнее хранилище сессий,
координация потребителей очереди и полноценная БД пользователей.
