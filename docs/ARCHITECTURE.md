Как устроен Max.

Браузер показывает интерфейс на React и Mantine. Он обращается к нашему
серверу Hono, а сервер делает запросы GREEN-API. Ключ провайдера
не передаётся обратно в браузер. Hono также отдаёт готовую сборку Vite.
TypeScript проверяет типы при сборке.

Код интерфейса находится в `webapp/src/`. Входной файл `main.tsx`
подключает `app`. Дальше код разделён по FSD. Это правило раскладки
файлов: каждая часть отвечает за свою задачу и использует нижние слои.
Так изменения формы отправки не требуют переписывать весь экран.

`app` подключает тему, стили и выбирает экран по состоянию входа.
`pages` содержит страницы входа, переписки и справки.
`widgets` собирает крупные блоки: рабочее место чатов и панель аккаунта.
`features` содержит действия пользователя: вход, подключение MAX,
написание сообщения, смену пароля и управление доступом.
`entities` описывает чаты, сообщения и пользователей.
`shared` содержит общие функции, запросы, схемы данных и элементы интерфейса.

Слои импортируют код только из нижних слоёв. Разные части одного слоя
не обращаются к внутренностям друг друга. Для внешних импортов есть
`index.ts`. Это позволяет менять внутренние файлы без правок
во всех местах, где используется компонент. Границы проверяются тестом.

Mantine даёт формы, кнопки, окна и темы. Иконки взяты из Tabler,
шрифт Manrope поставляется с приложением. CSS отвечает за расположение
чатов и оформление переписки. Есть светлая и тёмная темы.

В `contracts/` лежат схемы Zod: какие поля нужны, какой у них тип
и какие значения допустимы. Они проверяют запросы браузера, ответы сервера
и данные GREEN-API. Это нужно, потому что внешний сервис может вернуть
ответ с неожиданной структурой, даже если TypeScript-код собрался успешно.

В `types/` лежат типы, полученные из этих схем, и внутренние типы сервера.
Типы параметров компонентов находятся в отдельных `model/types.ts`.
Одну структуру данных не приходится вручную описывать дважды.
Браузер получает схемы через `shared/contracts` и проверяет ответ
перед передачей данных компонентам.

`server/app.ts` принимает HTTP-запросы, проверяет вход, права
и защиту от чужих запросов. `server/auth` отвечает за пароли,
пользователей и сессии. `server/lib` содержит обработку ошибок
и ограничение частоты запросов.

`src/max/client.ts` делает HTTPS-запросы GREEN-API.
`session.ts` управляет подключениями, историей, очередью и действиями
с сообщениями. `message.ts` преобразует данные провайдера в формат клиента.
`media.ts` проверяет файлы и скачивает их. `connections.ts` сохраняет
подключения, а `storage.ts` шифрует данные и записывает их на диск.

Пользователи хранятся в `DATA_DIR/users.json`. Вместо паролей сохраняются
scrypt-хеши с отдельной случайной солью для каждого пароля.
Соль мешает использовать одну готовую таблицу хешей для всех пользователей.
Хеши не выдаются через API. Запись сначала идёт в новый файл,
после чего он заменяет старый. Это уменьшает риск повреждения данных
при прерывании записи. Доступ к файлам ограничен правами 0600.

После входа сервер выдаёт подписанный JWT в HttpOnly-cookie.
JWT подтверждает, кто вошёл, а HttpOnly закрывает доступ к нему
из JavaScript страницы. Сервер дополнительно проверяет запись
о сессии и состояние пользователя при каждом запросе.

Реестр сессий хранится в `auth-sessions.enc`, ключ шифрования -
в `auth-sessions.key`. Поэтому перезапуск не завершает вход.
Cookie действует 365 дней и обновляется при запросе сессии,
если прошло не менее суток. Выход удаляет сессию из реестра.
Смена пароля и отзыв доступа делают старые токены недействительными.

Реквизиты MAX сохраняются в `max-connections.enc`, ключ шифрования -
в `max-connections.key`. Используется AES-256-GCM: он скрывает содержимое
и позволяет обнаружить его изменение. Каждый сохранённый инстанс
привязан к пользователю сервера. Повреждённый файл или потерянный ключ
не заменяются автоматически пустым хранилищем.

Подключение восстанавливается, когда пользователь открывает клиент.
Одновременные запросы используют одну попытку восстановления.
Временный сбой GREEN-API не удаляет ключ. Явное отключение удаляет ключ,
но оставляет адреса и номер инстанса для повторного входа.
Все файлы данных должны лежать в постоянном `DATA_DIR`.

После перезапуска создаётся новый `connectionId`.
Старая попытка отправки с прежним ID отклоняется: её нельзя безопасно
повторить после потери списка попыток в памяти. История, ссылки файлов
и результаты попыток отправки хранятся в памяти процесса.
История снова загружается у провайдера при выборе чата.

Уведомления читаются по одному. Событие сначала обрабатывается,
затем подтверждается в GREEN-API. Повтор одного события не создаёт дубль.
Исходные номера сообщений сохраняются. Поздний статус отправки
не заменяет уже известный статус прочтения.

Для текста, файла и пересылки используется `requestId` - номер попытки.
Повтор запроса с тем же номером не вызывает вторую отправку.
Если ответ провайдера потерян, клиент не отправляет сообщение
автоматически заново. Пользователь сначала проверяет переписку.

Хранилище рассчитано на один процесс и одну копию приложения.
Для нескольких копий понадобятся общая база данных и согласованная
работа с очередью. PostgreSQL и Redis в текущем клиенте не используются.

Внутренние пределы: 100 пользователей, 500 сессий сайта, 50 подключений MAX,
до 10000 чатов, контактов и сообщений на подключение,
300 попыток отправки за сессию. История провайдера ограничена
5000 событиями за три месяца. Опрос работает только в видимой вкладке.
Постоянный архив и уведомления при закрытом сайте не реализованы.

Mini App Советника использует те же основные части клиента,
но свой сервер и отдельное подключение. Одновременное чтение одной
очереди сайтом и Mini App может разделить ответы между ними.
